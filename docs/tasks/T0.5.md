# Objetivo
CI con E2E real y script de deploy contra Coolify.

# Contexto
El CI actual (`.github/workflows/ci.yml`) corre typecheck, lint, test y build. Existe un self-test E2E (`scripts/e2e-selftest.mjs`, `pnpm test:e2e`) que necesita la app viva con mocks (`WA_MOCK_ENABLED=true`, `META_GRAPH_BASE_URL` → wa-mock, `OPENROUTER_BASE_URL` → ai-mock; ver `specs/001-vocero-core/quickstart.md` y `CLAUDE.md`). Producción y staging viven en Coolify (API en `$COOLIFY_URL/api/v1`); no hay Caddy ni compose en producción.

# Archivos
- Modifica: `.github/workflows/ci.yml`, `docker-compose.yml` (imagen postgres → `pgvector/pgvector:pg16`), `.gitignore` (añadir `.env.deploy`), `README.md` (sección corta "Deploy en Coolify").
- Crea: `scripts/deploy.sh`, `.env.deploy.example`.
- Prohibido: `src/**`, `drizzle/**`.

# Especificación técnica
1. Job `e2e` en CI (después de build, mismo workflow): service container `pgvector/pgvector:pg16` con `POSTGRES_DB=vocero`; pasos: `pnpm install`, `pnpm db:migrate`, `pnpm build`, `pnpm start &` con las variables de mocks y secretos dummy generados en el job, esperar `curl -fsS localhost:3000/api/health` (máx 60 s), `pnpm test:e2e`. Sube `playwright-report`/capturas como artifact si falla.
2. `scripts/deploy.sh <prod|staging>`: lee `.env.deploy` (`COOLIFY_URL`, `COOLIFY_TOKEN`, `COOLIFY_APP_UUID_PROD`, `COOLIFY_APP_UUID_STAGING`, `HEALTH_URL_PROD`, `HEALTH_URL_STAGING`); hace `POST $COOLIFY_URL/api/v1/deploy?uuid=<uuid>`, extrae `deployment_uuid`, hace polling a `GET /api/v1/deployments/<uuid>` cada 15 s hasta `finished`/`failed` (máx 10 min), luego espera `HEALTH_URL` con 200 e imprime `version` y `commit` del JSON de `/api/health`. Sale con código ≠ 0 si falla. Sin dependencias fuera de bash + curl + jq (o python3).
3. `.env.deploy.example` con las claves anteriores y valores `REEMPLAZA_...`.

# Criterios de aceptación
1. CI verde en la rama del PR con el job `e2e` ejecutando el self-test real.
2. `bash -n scripts/deploy.sh` OK; `scripts/deploy.sh staging` con un `.env.deploy` válido (QA lo prueba) despliega y termina en 0.
3. `docker compose config` valida con la nueva imagen.

# Verificación
```bash
pnpm typecheck && pnpm lint && pnpm test && pnpm build
act -j e2e   # opcional si tienes act; si no, confía en el CI del PR
bash -n scripts/deploy.sh
```

## Reglas duras (obligatorias)

1. No ejecutes `pnpm db:generate`. Cambia solo `src/lib/db/schema/*.ts`; QA genera la migración al integrar.
2. Tablas nuevas en `src/lib/db/schema/<feature>.ts` + `export * from "./schema/<feature>"` en `src/lib/db/schema.ts`.
3. Toda query de dominio usa `scoped(schema.tabla.organizationId, organizationId, ...)` de `src/lib/db/tenant.ts`. Toda tabla nueva lleva `organization_id NOT NULL` con FK cascade a `organization`.
4. Secretos cifrados con `src/lib/crypto`. Nunca al cliente ni a logs.
5. Terceros nuevos = conector opcional tras bandera de entorno, apagado por defecto, 404 cuando está apagado.
6. Conversaciones `is_test` jamás tocan APIs reales. No toques ese guardrail.
7. Solo tocas los archivos listados en este brief. Si necesitas otro, dilo en el PR y para.
8. Gate antes de abrir PR: `pnpm typecheck && pnpm lint && pnpm test && pnpm build` en verde + tests unitarios de tu código + guion E2E en `tests/e2e/<us>.md` si hay flujo de usuario.
9. IDs con `newId("<entidad>")` registrando el prefijo donde viven los demás.
10. Español en UI, comentarios y docs; código y nombres de tablas en inglés.
11. Al terminar: commit (Conventional Commits en español), push, `gh pr create --base phase/1 --fill`, y escribe `DONE <número de PR>`. Si te bloqueas: `BLOCKED: <motivo>`.
