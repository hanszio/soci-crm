# Objetivo
Reemplazar el coalesce en memoria del agente por una cola persistente en Postgres (`agent_jobs`) con política de retraso "humano" (10 s a 5 min según intención y horario) e indicador "escribiendo…" antes de responder. Un reinicio del contenedor no pierde turnos.

# Contexto
- Hoy `src/server/ai/pipeline.ts` tiene `scheduleAgentTurn(conversationId)`: un `Map` global con `setTimeout` de `AGENT_COALESCE_MS` (6 s) y lock `running/pending` por conversación; luego `runAgentTurn(conversationId)` hace todo el turno. `src/server/ai/trigger.ts` (`maybeRunAgentTurn`) lo llama desde la ingesta (`src/server/inbox/ingest.ts`). El Laboratorio llama `runAgentTurn` directo y NO debe pasar por la cola.
- Indicador "escribiendo…": ver `src/app/api/bot/typing/route.ts` (usa `graphRequest` de `src/lib/meta/client.ts` con las credenciales de la org y el `wa_message_id` del último mensaje entrante). Extrae esa lógica a una función reutilizable `sendTypingIndicator(organizationId, conversationId)` en `src/server/inbox/typing.ts` y que la ruta del bot la use.
- `src/instrumentation.ts` ya existe y delega en `src/instrumentation-node.ts` (import dinámico solo con `NEXT_RUNTIME === "nodejs"`, donde hoy corre `cleanupOrphanRuns`): arranca el poller ahí, después de esa limpieza.
- T1.1 ya dejó `chatJson(..., { organizationId, kind })` y `isAiAvailable(org)`; no toques `src/lib/ai/**`.
- `agentProfile` vive en `src/lib/db/schema.ts` (tabla `agent_profile`). Las tablas nuevas van en `src/lib/db/schema/jobs.ts` re-exportadas desde `schema.ts` (ver cómo se hizo con `schema/ai.ts`).
- Conversaciones `is_test` (Laboratorio) jamás pasan por la cola ni envían typing.

# Especificación técnica
1. Tabla `agent_jobs(id text pk, organization_id text not null fk cascade, kind text not null, payload jsonb not null, run_at timestamptz not null, status text not null enum queued|running|done|failed|cancelled default queued, attempts int default 0, max_attempts int default 3, last_error text, locked_at timestamptz, created_at, updated_at)`. Índices: `(status, run_at)`; único parcial `(kind, (payload->>'conversationId')) WHERE status = 'queued'` (una conversación, un turno pendiente). En Drizzle el índice parcial se declara con `.where(sql\`...\`)`.
2. `queue.ts`: `enqueueOrReschedule({ organizationId, kind: "agent_turn", payload: { conversationId }, runAt })` → si ya hay job `queued` para esa conversación, actualiza `run_at` y `payload`; si hay uno `running`, crea otro `queued` (equivale al `pending` actual). `cancelForConversation(conversationId)`. Tipos exportados `JobKind = "agent_turn" | "typing"` (los otros kinds los añaden fases siguientes).
3. `poller.ts`: `startJobPoller()` idempotente (guard en `globalThis`), cada 2 s: `UPDATE agent_jobs SET status='running', locked_at=now(), attempts=attempts+1 WHERE id IN (SELECT id FROM agent_jobs WHERE status='queued' AND run_at <= now() ORDER BY run_at LIMIT 5 FOR UPDATE SKIP LOCKED) RETURNING *`; despacha por `kind` con un registro `handlers`; éxito → `done`; error → `failed` si `attempts >= max_attempts`, si no vuelve a `queued` con `run_at = now() + 2^attempts min`. Jobs `running` con `locked_at < now() - 10 min` vuelven a `queued` (proceso muerto). Heartbeat: escribe `process.env.__JOBS_LAST_TICK` o una fila en memoria consultable por `/api/health` (añade `jobs: { lastTickAt }` al JSON de health sin romper el formato actual).
4. `agentProfile` columnas nuevas (con defaults, sin romper filas existentes): `delay_min_sec int default 10`, `delay_max_sec int default 300`, `timezone text default 'America/Lima'`, `business_hours jsonb` (forma `{ "mon": [["09:00","19:00"]], ..., "sun": [] }`; null = siempre abierto), `out_of_hours_mode text enum reply|delay|silent default 'delay'`, `out_of_hours_message text`.
5. `delay.ts`: `estimateIntent(text): "greeting" | "faq" | "booking" | "other"` por heurística (longitud, saludos, palabras "cita/agendar/reunión/horario", signos de interrogación). `computeDelaySeconds({ intent, estimatedChars, profile, now })`: base `greeting` 10–25, `faq` 30–90, `booking` 60–180, `other` 20–60 (uniforme dentro del rango); `+ min(60, estimatedChars / 25)` donde `estimatedChars` = largo del último mensaje × 2; jitter ±20 %; fuera de horario según `out_of_hours_mode`: `delay` → `delay_max_sec`, `reply` → 10 s y el pipeline antepone `out_of_hours_message` (si existe) a la respuesta, `silent` → no encolar. Clamp final `[delay_min_sec, delay_max_sec]`. `AGENT_DELAY_MODE=instant` → 0 s siempre (tests y demos). Zona horaria con `Intl.DateTimeFormat` (sin dependencias nuevas).
6. `scheduleAgentTurn(conversationId)` pasa a: cargar conversación + perfil, calcular retraso, `enqueueOrReschedule` con `run_at = now + delay`. Si el cliente escribe otra vez antes de `run_at`, se recalcula y se pospone (reemplaza el coalesce). Conserva el nombre y la firma para que `trigger.ts` no cambie de forma.
7. Typing: handler `agent_turn` primero envía `sendTypingIndicator` si faltan ≤ 25 s para responder; implementación simple: al despachar el job, enviar typing, esperar `min(25, delay_restante)` s con `setTimeout` dentro del handler solo si el retraso total es ≥ 30 s (si es menor, typing y responder seguido). Nunca para `is_test`. Un fallo del typing se loguea y no bloquea.
8. UI Agente: sección "Ritmo humano" con retraso mínimo/máximo (segundos), zona horaria (input con datalist de zonas de LatAm y España), horario por día (dos franjas máx), modo fuera de horario y mensaje. Validación `min < max`, `min ≥ 5`, `max ≤ 600`.
9. Migración: NO ejecutes `pnpm db:generate`; QA la genera.

# Criterios de aceptación
1. Test: dos mensajes en 3 s → un solo job `queued` con `run_at` pospuesto; tercer mensaje durante `running` → un segundo job `queued`.
2. Test: poller nuevo (simula reinicio) toma el job pendiente y lo ejecuta; job con `locked_at` viejo vuelve a `queued`.
3. Test `computeDelaySeconds`: rangos por intención, clamp, jitter dentro de ±20 %, fuera de horario en las tres modalidades, `instant` → 0.
4. E2E con mocks y `AGENT_DELAY_MODE=instant`: el self-test actual sigue 133/133. Con `human` y `delay_min_sec=5`: el mock recibe primero el typing y luego la respuesta, y el log muestra `[jobs] agent_turn en Ns`.
5. Laboratorio sigue llamando `runAgentTurn` directo y no crea jobs.
6. Gate verde; `/api/health` incluye `jobs.lastTickAt`.
