# Objetivo
Convertir `src/lib/db/schema.ts` en un índice de re-exports y repartir las tablas en módulos por grupo, sin cambiar el esquema de la base de datos.

# Contexto
Hoy todas las tablas Drizzle viven en un único `src/lib/db/schema.ts` (~1000 líneas). Las fases siguientes añaden tablas en paralelo desde varios agentes; un archivo único produce conflictos de merge. El resto del código importa `import { schema } from "@/lib/db"` (ver `src/lib/db/index.ts`) y eso debe seguir funcionando igual.

# Archivos
- Crea: `src/lib/db/schema/auth.ts`, `crm.ts`, `inbox.ts`, `channels.ts`, `agent.ts`, `agenda.ts`, `attribution.ts`.
- Modifica: `src/lib/db/schema.ts` (queda solo con `export * from "./schema/<grupo>"` por grupo), `src/lib/db/index.ts` solo si hace falta para conservar el símbolo `schema`.
- Prohibido: cualquier otro archivo; `drizzle/`.

# Especificación técnica
Reparto de tablas (nombres de las constantes exportadas tal cual existen hoy):
- auth.ts: user, session, account, verification, organization, member, invitation
- crm.ts: contact, pipelineStage, lead, leadStageEvent
- inbox.ts: conversation, message, mediaAsset, template
- channels.ts: metaCredentials, instagramCredentials, messengerCredentials
- agent.ts: agentProfile, kbEntry, agentTestRun, agentTestCase
- agenda.ts: calendarSettings, booking, offeredSlot, zoomCredentials, googleCredentials
- attribution.ts: adAttribution, conversionEvent, capiSettings

Las referencias cruzadas (`references(() => organization.id)`, etc.) se resuelven importando entre módulos; evita ciclos: auth no importa a nadie; los demás importan de auth y, si hace falta, de crm/inbox. Conserva comentarios y nombres de índices exactamente.

# Criterios de aceptación
1. `pnpm db:generate` NO produce ninguna migración nueva (salida "No schema changes"). Si produce alguna, el reparto está mal: corrígelo (no la commitees).
2. `pnpm typecheck && pnpm lint && pnpm test && pnpm build` en verde.
3. `grep -rn "from \"@/lib/db/schema\"" src` sigue compilando sin cambios en los consumidores.

# Verificación
```bash
pnpm install --frozen-lockfile
pnpm db:generate   # debe decir que no hay cambios; borra cualquier archivo generado
pnpm typecheck && pnpm lint && pnpm test && pnpm build
```

## Reglas duras (obligatorias)

1. No ejecutes `pnpm db:generate`. Cambia solo `src/lib/db/schema/*.ts`; QA genera la migración al integrar.
2. Tablas nuevas en `src/lib/db/schema/<feature>.ts` + `export * from "./schema/<feature>"` en `src/lib/db/schema.ts`.
3. Toda query de dominio usa `scoped(schema.tabla.organizationId, organizationId, ...)` de `src/lib/db/tenant.ts`. Toda tabla nueva lleva `organization_id NOT NULL` con FK cascade a `organization`.
4. Secretos cifrados con `src/lib/crypto`. Nunca al cliente ni a logs.
5. Terceros nuevos = conector opcional tras bandera de entorno, apagado por defecto, 404 cuando está apagado.
6. Conversaciones `is_test` jamás tocan APIs reales. No toques ese guardrail.
7. Solo tocas los archivos listados en este brief. Si necesitas otro, dilo en el PR y para.
8. Gate antes de abrir PR: `pnpm typecheck && pnpm lint && pnpm test && pnpm build` en verde + tests unitarios de tu código + guion E2E en `tests/e2e/<us>.md` si hay flujo de usuario.
9. IDs con `newId("<entidad>")` registrando el prefijo donde viven los demás.
10. Español en UI, comentarios y docs; código y nombres de tablas en inglés.
11. Al terminar: commit (Conventional Commits en español), push, `gh pr create --base phase/0 --fill`, y escribe `DONE <número de PR>`. Si te bloqueas: `BLOCKED: <motivo>`.
